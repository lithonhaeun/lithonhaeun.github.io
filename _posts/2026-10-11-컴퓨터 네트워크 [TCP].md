# TCP 들어가기

전편에서 이더넷, 와이파이, 스위치, 라우터처럼 데이터가 실제로 지나가는 기술들을 살펴봤다면,
여기서는 계층을 하나 올라가 전송 계층, 그중에서도 TCP를 다룹니다.

---

> ### 목차
>
> 1. 전송 계층 기초 (Transport Layer Basics)
>    - 전송 계층이 하는 일, TCP와 UDP의 차이, 포트 번호를 이용한 다중화와 역다중화(비연결형 / 연결형)를 정리합니다.
> 2. TCP 서비스 (TCP Services)
>    - TCP가 응용 계층에 제공하는 세 가지 서비스인 연결 지향, 신뢰성, 바이트 스트림을 살펴봅니다.
> 3. TCP 특징 (TCP Features)
>    - 순서 번호, 누적 ACK, 피기배킹, 재전송 타이머, 전이중 통신처럼 TCP가 신뢰성을 만들어 내는 방법을 알아봅니다.
> 4. TCP 헤더와 캡슐화 (TCP Header and Encapsulation)
>    - 포트 번호, 순서 번호, 확인 응답 번호, 플래그, 윈도 크기, 체크섬 등 TCP 헤더의 각 필드가 하는 일을 하나씩 봅니다.

## 1. 전송 계층 기초 (Transport Layer Basics)
### 전송 서비스와 프로토콜 (Transport Services and Protocols)

> 핵심
> 
> 전송 계층은 서로 다른 호스트에서 실행 중인 응용 프로세스들 사이에 논리적 통신을 제공한다.

- 전송 서비스와 프로토콜
  - 서로 다른 호스트에서 실행 중인 응용 프로세스 사이에 논리적 통신(logical communication)을 제공한다.
  - 전송 프로토콜은 종단 시스템(end system)에서 동작한다.
    - 송신자: 응용 메시지를 세그먼트(segment)로 나누어 네트워크 계층에 넘긴다.
    - 수신자: 세그먼트를 다시 메시지로 조립해 응용 계층에 넘긴다.
  - 인터넷 응용 프로그램이 쓸 수 있는 전송 프로토콜은 두 가지이다.
    - TCP, UDP

논리적 통신이란, 실제로는 데이터가 여러 라우터와 링크를 거쳐 가지만
응용 프로세스 입장에서는 상대 프로세스와 직접 연결된 것처럼 보인다는 뜻이다.

전송 계층에서 다루는 데이터 단위는 세그먼트이다.

### 송신자 쪽 전송 계층의 동작 (Transport Layer Actions: Sender)

> 핵심
> 
> 송신 측 전송 계층은 응용 메시지에 헤더를 붙여 세그먼트를 만들고, 이를 IP(네트워크 계층)에 넘긴다.

- 전송 계층의 동작
- 송신자는
  1. 응용 계층으로부터 메시지를 넘겨받는다.
  2. 세그먼트 헤더 필드의 값들을 정한다.
  3. 세그먼트를 만든다.
  4. 세그먼트를 IP에 넘긴다.

헤더 필드에 들어가는 대표적인 값이 출발지 포트 번호와 목적지 포트 번호이다.

|헤더	|PDU| 	적히는 것	                |무엇을 가리키나|
|---|---|------------------------|---|
|네트워크 계층 (IP) 헤더|	N-PDU (데이터그램)| 	출발지 IP 주소, 목적지 IP 주소  |	어느 컴퓨터|
|전송 계층 (TCP/UDP) 헤더|T-PDU (세그먼트)| 	출발지 포트 번호, 목적지 포트 번호	 | 그 컴퓨터 안의 어느 프로그램      |

### 수신자 쪽 전송 계층의 동작 (Transport Layer Actions: Receiver)

> 핵심
> 
> 수신 측 전송 계층은 IP로부터 받은 세그먼트의 헤더를 확인하고, 응용 메시지를 꺼내 소켓을 통해 알맞은 응용 프로그램에 올려 보낸다.

- 수신자는
  1. IP로부터 세그먼트를 받는다.
  2. 헤더 값들을 확인한다.
  3. 응용 계층 메시지를 꺼낸다.
  4. 소켓(socket)을 통해 메시지를 응용 프로그램으로 역다중화(demultiplex)해 올려 보낸다.

송신자가 헤더 값을 "정했다면", 수신자는 그 헤더 값을 "보고" 메시지를 어디로 보낼지 결정한다.
이때 여러 프로그램 중 알맞은 하나를 골라 넘겨주는 것을 역다중화라고 한다.

소켓은 응용 프로그램과 전송 계층 사이의 출입구이다.

### 인터넷의 두 전송 프로토콜 (Two Principal Internet Transport Protocols)

> 핵심
> 
> TCP는 신뢰성 있고 순서가 보장되는 전달을, UDP는 신뢰성도 순서도 보장하지 않는 단순한 전달을 제공한다. 둘 다 지연과 대역폭은 보장하지 않는다.

- 인터넷의 두 가지 주요 전송 프로토콜
  - TCP: 전송 제어 프로토콜 (Transmission Control Protocol)
    - 신뢰성 있고, 순서대로 전달 (reliable, in-order delivery)
      - 패킷 손실시 재전송
      - 최종 전송 실패시 알려줌
    - 혼잡 제어 (congestion control)(보내는 양)
    - 흐름 제어 (flow control)(데이터량)
    - 연결 설정 (connection setup)
  - UDP: 사용자 데이터그램 프로토콜 (User Datagram Protocol)
    - 신뢰성 없고, 순서 없는 전달 (unreliable, unordered delivery)
    - "최선형(best-effort)" IP에 군더더기 없이 기능만 조금 더한 것 (no-frills extension)
  - 제공되지 않는 서비스
    - 지연 보장 (delay guarantees)
    - 대역폭 보장 (bandwidth guarantees)

| 구분 | TCP | UDP |
|---|---|---|
| 신뢰성 | 있음 (잃어버리면 다시 보냄) | 없음 |
| 순서 | 보장 | 보장 안 함 |
| 연결 설정 | 있음 | 없음 |
| 흐름 제어 | 있음 | 없음 |
| 혼잡 제어 | 있음 | 없음 |
| 지연, 대역폭 보장 | 없음 | 없음 |

UDP는 IP가 하는 최선형 전달에 포트 번호(프로세스 구분)와 체크섬 정도만 더한 프로토콜이다.
TCP는 그 위에 신뢰성, 순서 보장, 연결 관리, 흐름 제어, 혼잡 제어까지 직접 해 준다.

두 프로토콜 모두 "얼마 안에 도착한다"거나 "초당 얼마 이상 보낸다"는 약속은 하지 못한다.

### TCP/IP 프로토콜 스위트 속의 TCP

![](/assets/img/20261012-capture.png)

TCP/IP 프로토콜 스위트는 계층마다 여러 프로토콜이 모여 있는 묶음이다.

이 중 TCP는 전송 계층에 있으며, HTTP, SMTP, FTP처럼 데이터를 빠짐없이 받아야 하는 응용 프로토콜들이 TCP 위에서 동작한다.
"TCP/IP"라는 이름 자체가 전송 계층의 TCP와 네트워크 계층의 IP에서 따온 것이다.

### 다중화와 역다중화 (Multiplexing and Demultiplexing)

> 핵심
> 
> 호스트의 전송 계층은 보낼 때 다중화를, 받을 때 역다중화를 수행한다.

- 호스트의 전송 계층은 다중화와 역다중화를 수행한다.
- 송신자의 다중화 (multiplexing as sender)
  - 여러 소켓에서 온 데이터를 처리하고, 전송 헤더를 붙인다. (이 헤더는 나중에 역다중화에 쓰인다.)
- 수신자의 역다중화 (demultiplexing as receiver)
  - 헤더 정보를 이용해, 받은 세그먼트를 올바른 소켓에 전달한다.

그림에는 세 대의 호스트가 있고, 그중 한 호스트에서는 프로세스 P1, P2가 동시에 네트워크를 쓰고 있다.

| 역할 | 하는 일 | 쓰는 정보 |
|---|---|---|
| 다중화 (송신) | 여러 소켓의 데이터를 모아 헤더를 붙이고 하나의 네트워크 계층으로 내려보냄 | 헤더에 포트 번호를 적음 |
| 역다중화 (수신) | 도착한 세그먼트를 알맞은 소켓으로 나눠 줌 | 헤더의 포트 번호를 읽음 |

송신자가 헤더에 적은 값이, 수신자가 역다중화할 때 보는 값이 된다.
그래서 다중화와 역다중화는 항상 짝으로 동작한다.

### 어느 프로세스로 보낼까? (Which Process?)

질문: 전송 계층은 메시지를 Netflix 프로세스나 Skype 프로세스가 아니라 Firefox 브라우저 프로세스에 전달해야 한다는 것을 어떻게 알았을까?

### 전송 계층의 다중화 (Multiplexing in Transport Layer)

> 핵심
> 
> 호스트는 IP 주소와 포트 번호를 함께 사용해, 도착한 세그먼트를 알맞은 소켓으로 보낸다.

- 호스트는 IP 데이터그램을 받는다.
  - 각 데이터그램에는 출발지 IP 주소와 목적지 IP 주소가 있다.
  - 각 데이터그램은 전송 계층 세그먼트를 하나씩 싣고 있다.
  - 각 세그먼트에는 출발지 포트 번호와 목적지 포트 번호가 있다.
- 호스트는 IP 주소와 포트 번호를 이용해 세그먼트를 알맞은 소켓으로 보낸다.

TCP/UDP 세그먼트 형식 (32비트 너비)<br>
데이터그램 하나 안에 세그먼트 하나가 들어 있는 구조이다.

| 정보 | 들어 있는 곳 |
|---|---|
| 출발지 / 목적지 IP 주소 | IP 데이터그램 헤더 (네트워크 계층) |
| 출발지 / 목적지 포트 번호 | TCP/UDP 세그먼트 헤더 (전송 계층) |

세그먼트 헤더의 맨 앞에는 TCP든 UDP든 출발지 포트 번호와 목적지 포트 번호가 온다.
포트 번호는 각각 16비트라서, 두 개를 합쳐 첫 줄(32비트)을 채운다.

소켓을 찾을 때는 두 헤더에 나뉘어 있는 IP 주소와 포트 번호를 함께 본다.

### 비연결형 역다중화 (Connectionless Demultiplexing)

> 핵심
> 
> UDP는 목적지 포트 번호만 보고 소켓을 찾는다. 그래서 출발지가 달라도 목적지 포트 번호가 같으면 모두 같은 소켓으로 들어간다.

- 비연결형 역다중화 (UDP가 사용)
  - 다중화 규칙: UDP 소켓으로 보낼 데이터그램을 만들 때, 반드시 다음을 지정해야 한다.
    - 목적지 IP 주소
    - 목적지 포트 번호
  - 역다중화 규칙: 수신 호스트가 UDP 세그먼트를 받으면
    - 세그먼트의 목적지 포트 번호를 확인한다.
    - 그 포트 번호를 가진 소켓으로 UDP 세그먼트를 보낸다.
- 목적지 포트 번호가 같은 IP/UDP 데이터그램은, 출발지 IP 주소나 출발지 포트 번호가 달라도 수신 호스트에서 같은 소켓으로 전달된다.

| 구분 | 보내는 쪽이 지정하는 것 | 받는 쪽이 보는 것 |
|---|---|---|
| UDP | 목적지 IP 주소, 목적지 포트 번호 | 목적지 포트 번호 |

데이터그램이 이미 이 호스트에 도착했다면 목적지 IP 주소는 당연히 자기 자신이므로,
UDP 소켓을 고를 때 실제로 구분에 쓰이는 값은 목적지 포트 번호 하나이다.

그 결과, 여러 클라이언트가 같은 포트로 보낸 데이터가 모두 하나의 소켓으로 모인다.
누가 보냈는지는 소켓이 아니라 응용 프로그램이 데이터그램의 출발지 정보를 보고 구분해야 한다.

즉 : source port 는 적절한 소켓에 세그먼트의 데이터를 전달하는 과정에서 관여하지 않는다

### 연결형 역다중화 (Connection-oriented Demultiplexing)

> 핵심
> 
> TCP 연결은 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트의 4-튜플로 구분되며, 수신자는 이 네 값을 모두 사용해 세그먼트를 알맞은 소켓으로 보낸다

- 연결형 역다중화
  - RFC 793에 따르면, 소켓, 순서 번호, 윈도 크기 등 각 데이터 스트림(tcp에서 데이터 흐름)의 상태 정보를 묶은 것을 연결(connection)이라고 한다.
  - 소켓 한 쌍(로컬 소켓과 원격 소켓)이 각 TCP 연결을 유일하게 구분한다.
    - 출발지 IP 주소
    - 출발지 포트 번호
    - 목적지 IP 주소
    - 목적지 포트 번호
  - 다중화 규칙: 송신자가 TCP 세그먼트를 담은 IP 데이터그램을 만들 때, TCP/IP 헤더에 위의 4-튜플이 나뉘어 들어간다.
  - 역다중화 규칙: 수신자는 네 값(4-튜플)을 모두 사용해 TCP 세그먼트를 알맞은 소켓으로 보낸다.
  - 이 규칙 덕분에 서버는 동시에 많은 TCP 소켓을 운영할 수 있다.
    - 각 소켓은 자기만의 4-튜플로 구분된다.
    - 각 소켓은 서로 다른 접속 클라이언트와 연결된다.

4-튜플은 두 헤더에 나뉘어 들어 있다.

| 값 | 들어 있는 헤더 |
|---|---|
| 출발지 IP 주소, 목적지 IP 주소 | IP 헤더 (네트워크 계층) |
| 출발지 포트 번호, 목적지 포트 번호 | TCP 헤더 (전송 계층) |

UDP와 TCP의 역다중화를 비교하면 다음과 같다.

| 구분 | 소켓을 고를 때 보는 값 | 결과 |
|---|---|---|
| UDP (비연결형) | 목적지 포트 번호 | 출발지가 달라도 같은 소켓 |
| TCP (연결형) | 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트 | 출발지가 다르면 다른 소켓 |

연결이란 단순히 주소 쌍만이 아니라, 그 사이에서 주고받는 데이터의 상태(순서 번호, 윈도 크기 등)까지 포함한 개념이다.
### 연결형 역다중화 예제 (Connection-oriented Demultiplexing: Example)

> 핵심
> 
> 목적지 IP 주소(B)와 목적지 포트(80)가 모두 같은 세그먼트 세 개가, 4-튜플이 달라서 서버의 서로 다른 소켓으로 역다중화된다.

- 세 세그먼트 모두 목적지 IP 주소 B, 목적지 포트 80으로 향하지만, 서로 다른 소켓으로 역다중화된다.

![](/assets/img/20261012-capture-2.png)


세 세그먼트는 목적지(B, 80)가 모두 같다.
차이는 출발지에 있다.

- A의 P1과 C의 P3은 출발지 포트(9157)가 같지만 출발지 IP(A, C)가 다르다.
- C의 P2와 C의 P3은 출발지 IP(C)가 같지만 출발지 포트(5775, 9157)가 다르다.

네 값 중 하나만 달라도 다른 연결이므로, 서버는 세 세그먼트를 각각 P4, P6, P5의 소켓으로 보낸다.
서버의 소켓 세 개는 모두 같은 포트 80을 쓰지만, 4-튜플이 달라서 서로 구분된다.

UDP였다면 목적지 포트(80)만 보므로 셋 다 같은 소켓으로 들어갔을 것이다.

## 2. TCP 서비스 (TCP Services)

전송 계층의 기본 역할을 봤으니, 이제 TCP가 응용 계층에 무엇을 제공하는지 살펴본다.
TCP의 서비스는 연결 지향, 신뢰성, 바이트 스트림 세 가지로 요약된다.

### TCP가 제공하는 서비스 (TCP Services)

> 핵심
> 
> TCP는 <mark class="pink">connection-oriented </mark>(연결 지향적)이고, 
> <mark class="pink">reliable </mark>(신뢰성 있는), 
> <mark class="pink">byte stream service </mark>(바이트 스트림 서비스)를 제공한다.

- TCP는 연결 지향(connection-oriented), 신뢰성(reliable), 바이트 스트림(byte stream) 서비스를 제공한다.
  - TCP와 UDP는 같은 네트워크 계층(IP)을 사용하지만,
  - TCP는 응용 계층에 UDP와 완전히 다른 서비스를 제공한다.

| 서비스 | 의미 | UDP와 비교 |
|---|---|---|
| 연결 지향 | 데이터를 주고받기 전에 서로 연결을 맺는다 | UDP는 연결 없이 바로 보낸다 |
| 신뢰성 | 데이터가 빠짐없이, 순서대로, 깨지지 않고 도착하게 한다 | UDP는 도착을 보장하지 않는다 |
| 바이트 스트림 | 데이터를 메시지 단위가 아니라 끊김 없는 바이트의 흐름으로 다룬다 | UDP는 메시지(데이터그램) 단위로 보낸다 |

TCP와 UDP 아래의 IP는 똑같이 비연결, 최선형 전달을 한다.
같은 IP 위에서 UDP는 거의 그대로 전달하고, TCP는 위의 세 가지 서비스를 직접 만들어 낸다.

### 연결 지향의 의미 (Connection-oriented)

> 핵심
> 
> TCP를 쓰는 두 응용 프로그램은 데이터를 주고받기 전에 반드시 연결을 맺어야 하며, 하나의 TCP 연결에는 정확히 두 개의 끝점만 있다.

- 연결 지향이란
  - TCP를 사용하는 두 응용 프로그램은 데이터를 주고받기 전에, 서로 연락해 연결을 맺어야 한다.
  - 하나의 TCP 연결에서 통신하는 끝점(endpoint)은 정확히 두 개이다.
    - 연결은 두 끝점 사이에 동기화된 상태(synchronized states)로 여겨진다.
      - tcp는 상태를 저장한다.
### 바이트 스트림 서비스 (Byte Stream)

> 핵심
> 
> TCP는 응용 프로그램에 바이트 스트림이라는 추상화를 제공한다. TCP는 바이트의 내용을 해석하지 않고, 메시지 경계도 표시하지 않는다.

- TCP는 응용 프로그램에 바이트 스트림 추상화(abstraction)를 제공한다.
  - TCP는 바이트 스트림 안의 바이트 내용을 전혀 해석하지 않는다.
  - TCP는 레코드 표시(record marker)나 메시지 경계(message boundary)를 자동으로 넣지 않는다.
    - 레코드 표시란 응용 프로그램이 한 번에 쓴(write) 범위를 나타내는 표시이다.
    - 각 끝점은 읽고 쓰는 크기를 각자 따로 정한다.
  - 전이중(full duplex) 서비스: 8비트 바이트의 흐름이 연결의 양방향으로 오가며, 각 방향은 반대 방향과 독립적이다.
    - duplex : 양방향 데이터 교환
      - half : ~오바 처럼 끝났다는거 알려줌 (동시 전송 x)
      - full : 상대 상태 상관 없이 동시에 보내는거 가능
    - simplex : 한방향 데이터 교환

TCP는 응용 프로그램이 몇 번에 나눠 썼는지를 기억하지 않는다.
예를 들어 송신 측이 데이터를 10바이트, 20바이트, 50바이트로 세 번 써도,

전이중이란 A → B 방향과 B → A 방향의 바이트 흐름이 동시에, 서로 독립적으로 오갈 수 있다는 뜻이다.

### 신뢰성 1: 패킷화와 재전송 (Reliability: Packetization and ARQ)

> 핵심
> 
> TCP는 바이트 스트림을 IP가 실어 나를 수 있는 세그먼트로 나누고(패킷화), 각 세그먼트에 바이트 단위의 순서 번호를 붙이며, 잃어버린 데이터는 재전송으로 복구한다.

- TCP는 다음 방법으로 신뢰성을 제공한다.
  - 패킷화(packetization): 보낼 바이트 스트림을 IP가 운반할 수 있는 세그먼트들로 바꾼다.
    - 세그먼트에는 순서 번호(sequence number)가 들어 있다. TCP의 순서 번호는 패킷 번호가 아니라, 각 세그먼트의 첫 번째 바이트가 전체 데이터 스트림에서 몇 번째 바이트인지(바이트 오프셋)를 나타낸다.
    - 응용 데이터는 TCP가 판단한 가장 알맞은 크기로 나뉜다. (양 끝점의 정보만 사용)
      각 세그먼트는 단편화(fragmentation)되지 않을 크기로, IP 데이터그램 하나에 들어가도록 맞춘다.
  - 재전송 메커니즘을 가진 Go-Back-N 자동 재전송 요청(ARQ)의 변형

| 방법 | 하는 일 |
|---|---|
| 패킷화 | 바이트 스트림을 적당한 크기의 세그먼트로 자른다 |
| 순서 번호 | 각 세그먼트의 첫 바이트가 전체에서 몇 번째 바이트인지 적는다 |
| 크기 조절 | IP 데이터그램 하나에 들어가고, 중간에 쪼개지지 않을 크기로 자른다 |
| 재전송 (ARQ) | 확인 응답이 오지 않으면 다시 보낸다 |

순서 번호가 "몇 번째 세그먼트"가 아니라 "몇 번째 바이트"라는 점이 TCP의 특징이다.
이는 TCP가 데이터를 메시지가 아닌 바이트 스트림으로 다루기 때문이다.

### 신뢰성 2: 체크섬 (Reliability: Checksum)

> 핵심
> 
> TCP는 헤더, 데이터, IP 헤더의 일부 필드까지 포함하는 체크섬을 반드시 계산하며, 체크섬이 맞지 않는 세그먼트는 ACK 없이 버린다.

- TCP는 다음 방법으로도 신뢰성을 제공한다. (계속)
  - TCP는 헤더, 함께 실린 응용 데이터, 그리고 IP 헤더의 일부 필드에 대해 필수(mandatory) 체크섬을 유지한다.
    - UDP의 의사 헤더(pseudo-header) 방식과 비슷하다.
    - 체크섬이 틀린 세그먼트는 ACK를 보내지 않고 버린다.
    - 대용량 데이터 전송에서는 이 체크섬이 충분히 강력하지 않다는 우려가 있다 [SP00].
      따라서 신중한 응용 프로그램은 더 강한 체크섬이나 CRC 같은 자체 오류 보호 방법을 쓰거나, 미들웨어 계층(예: RFC 5044)을 사용해야 한다.
      

| 항목 | 내용 |
|---|---|
| 계산 범위 | TCP 헤더 + 데이터 + IP 헤더의 일부(의사 헤더) |
| 틀렸을 때 | 버리고 ACK를 보내지 않음 → 송신자가 재전송 |
| 한계 | 단순한 덧셈 기반이라 일부 오류는 못 잡음 |

체크섬이 틀린 세그먼트에 ACK를 보내지 않으면, 송신자는 확인 응답을 받지 못해 결국 다시 보낸다.
즉 체크섬(오류 검출)과 재전송(오류 복구)이 함께 동작해 신뢰성을 만든다.

## 3. TCP 특징 (TCP Features)

TCP가 제공하는 서비스를 봤으니, 이제 그 서비스를 만들어 내는 구체적인 동작을 살펴본다.
순서 번호, ACK와 피기배킹, 누적 ACK, 재전송 타이머, 중복 제거와 순서 재정렬, 전이중 통신을 차례로 다룬다.

> 핵심
> 
> TCP의 순서 번호는 세그먼트 번호가 아니라, 각 세그먼트의 첫 번째 바이트가 전체 데이터 스트림에서 갖는 바이트 번호이다.


### 확인 응답과 피기배킹 (ACK and Piggybacking)

> 핵심
> 
> TCP는 상대에게서 데이터를 받으면 확인 응답(ACK)을 보내며, 이 ACK는 상대에게 보내는 데이터 세그먼트에 함께 실어 보낼 수도 있다. 이를 피기배킹이라고 한다.


- TCP는 연결의 상대편으로부터 데이터를 받으면, 상대편에 확인 응답(ACK, acknowledgment) 세그먼트를 보낸다.
  - 이 ACK는 상대편으로 가는 데이터 세그먼트 안에 함께 담길 수도 있다.
    - 이 기법을 피기배킹(piggybacking)이라고 한다.
      - segment 일부분에 보냄

| 방식 | 보내는 세그먼트 | 특징 |
|---|---|---|
| 따로 ACK | 데이터 세그먼트 따로, ACK만 담은 세그먼트 따로 | 세그먼트 수가 많아짐 |
| 피기배킹 | 데이터 세그먼트 하나에 ACK를 함께 담음 | 세그먼트 수가 줄어 효율적 |

ACK는 "여기까지 잘 받았다"는 수취영수증과 같다.
B가 A에게 보낼 데이터가 있다면, 영수증을 따로 보내지 않고 그 데이터에 붙여서 보낸다.

### 누적 ACK (Cumulative ACK)

> 핵심
> 
> TCP의 ACK는 누적형이다. ACK 번호 N은 N번 바로 앞 바이트까지 모두 잘 받았다는 뜻이므로, 중간에 ACK 하나를 잃어버려도 다음 ACK가 이를 대신한다.

- 누적 ACK (Cumulative ACK)
  - ACK는 바로 보내지 않고, 보통 1초 미만의 짧은 시간 동안 지연된 뒤 보낸다.
  - TCP가 쓰는 ACK는 누적형(cumulative)이다.
    바이트 번호 N을 가리키는 ACK는, N번 직전 바이트까지(N은 포함하지 않음) 모든 바이트를 이미 성공적으로 받았다는 뜻이다.
  - 이 방식은 ACK 손실에 어느 정도 강하다(robustness).

![](/assets/img/20261013-capture.png)


누적 ACK가 ACK 손실에 강한 이유는 책 읽기에 비유하면 쉽게 이해할 수 있다.
친구에게 "100쪽까지 읽었어", "200쪽까지 읽었어", "300쪽까지 읽었어"라고 차례로 문자를 보냈는데, 두 번째 문자가 전달되지 않았다고 하자.
그래도 친구는 세 번째 문자 "300쪽까지 읽었어"를 받으면 200쪽까지도 당연히 읽었다는 것을 알 수 있다.
반면 선택적 ACK처럼 "2장 읽었어"라고 하나씩 따로 알리는 방식이라면, 그 문자가 사라졌을 때 2장을 읽었는지 알 방법이 없다.

하지만 누적 ACK에도 약점이 있다.
중간 세그먼트 하나가 빠지면, 그 뒤의 세그먼트를 아무리 많이 받아도 ACK 번호가 올라가지 않는다.
예를 들어 #201이 사라지고 #301이 도착하면, 수신자는 여전히 ACK#201만 보낼 수 있다.
이 문제를 보완하기 위해 현대의 TCP는 선택적 ACK(SACK)를 옵션으로 함께 사용한다.


### 재전송 타이머 (Retransmission Timer)

> 핵심
> 
> TCP는 세그먼트를 보내면 타이머를 켜고 ACK를 기다리며, 시간 안에 ACK가 오지 않으면 다시 보낸다. 여러 세그먼트를 보낼 때도 세그먼트마다가 아니라 보통 타이머 하나만 쓴다.

- TCP는 세그먼트를 보낼 때 타이머를 유지하며, 상대편이 그 세그먼트를 받았다고 확인해 주기를 기다린다.
  - 제시간에 ACK를 받지 못하면, 그 세그먼트를 재전송한다.
- TCP는 여러 세그먼트를 한 번에 보낼 때, 보통 재전송 타이머를 하나만 설정하고 상대편의 확인을 기다린다.
  - 즉, TCP는 세그먼트마다 다른 타이머를 따로 두지 않는다.



| 상황 | TCP의 동작 |
|---|---|
| 세그먼트를 보냄 | 재전송 타이머 시작 |
| 시간 안에 ACK 도착 | 타이머 정리 (아직 확인 안 된 데이터가 남아 있으면 다시 시작) |
| 시간 안에 ACK가 안 옴 (타임아웃) | 확인되지 않은 세그먼트를 재전송 |

타이머를 하나만 쓸 수 있는 이유는 ACK가 누적형이기 때문이다.
ACK 하나로 "여기까지 다 받았다"를 알 수 있으므로, 가장 오래된 미확인 데이터 하나만 지켜보면 된다.

### 중복 ACK (Duplicate ACK)

> 핵심
> 
> 수신 측 TCP는 이미 ACK한 세그먼트를 다시 ACK할 수도 있으며, 이는 송신자의 혼잡 제어 계산을 돕기 위해서이다.

![](/assets/img/20261013-capture-2.png)


- 한편, 수신 측 TCP는 이전에 이미 ACK한 세그먼트를 다시 확인 응답할 수도 있다.
  - 송신자의 혼잡 제어 계산을 돕기 위해서이다.


송신자는 같은 ACK가 반복해서 오는 것을 보고 다음을 알 수 있다.
- 201번 바이트부터 시작하는 세그먼트가 사라졌을 가능성이 높다.
- 그 뒤의 세그먼트들은 계속 도착하고 있으므로, 네트워크가 완전히 막힌 것은 아니다.

이 정보는 재전송과 혼잡 제어에 활용된다.

### 중복 제거와 순서 재정렬 (Discarding Duplicates and Reordering)

> 핵심
> 
> 수신 측 TCP는 순서 번호를 이용해 중복된 세그먼트는 버리고, 순서가 뒤바뀌어 도착한 세그먼트는 원래 순서대로 다시 정렬한다.

- 수신 측 TCP는 순서 번호를 이용해 중복 세그먼트를 버리고(discard), 순서가 어긋나게 도착한 세그먼트를 다시 정렬한다.

IP는 비연결, 최선형 전달이므로 다음과 같은 일이 생길 수 있다.

| 상황 | 원인 | 수신 측 TCP의 처리            |
|---|---|-------------------------|
| 같은 세그먼트가 두 번 도착 | ACK가 늦거나 사라져 송신자가 재전송함 | 이미 받은 순서 번호이므로 버림(폐기처분) |
| 순서가 뒤바뀌어 도착 | 패킷마다 다른 경로로 가거나 지연이 다름 | 버퍼에 잠시 두었다가 순서 번호대로 정렬  |

순서 번호가 바이트 위치를 나타내기 때문에, 수신자는 각 세그먼트가 스트림의 어디에 들어갈지 정확히 알 수 있다.
이렇게 정리한 뒤에야 응용 프로그램에 데이터를 순서대로 넘긴다.

### 전이중 서비스 (Full-duplex Service)

> 핵심
> 
> TCP 연결에서는 양방향으로 데이터가 독립적으로 흐르며, 각 끝점은 방향마다 순서 번호를 따로 관리하고, 연결이 맺어진 뒤의 모든 세그먼트에는 반대 방향에 대한 ACK가 함께 들어간다.

번역

- 전이중(full-duplex) 서비스: 데이터가 각 방향으로 독립적으로 흐를 수 있다.
  - 각 끝점은 방향마다 흐르는 데이터의 순서 번호를 따로 유지해야 한다.
  - 연결이 한 번 맺어지면, 한 방향으로 흐르는 모든 TCP 세그먼트에는 반대 방향으로 흐르는 세그먼트에 대한 ACK가 함께 들어간다.

| 방향 | 순서 번호가 가리키는 것 | ACK 번호가 가리키는 것 |
|---|---|---|
| A → B 세그먼트 | A가 보내는 데이터의 바이트 위치 | B에게서 받은 데이터 중 다음에 받을 바이트 |
| B → A 세그먼트 | B가 보내는 데이터의 바이트 위치 | A에게서 받은 데이터 중 다음에 받을 바이트 |

예를 들어 A가 B에게 보내는 세그먼트에는 다음 두 정보가 동시에 들어 있다.

- 순서 번호: "이 데이터는 내 스트림의 몇 번째 바이트부터야"
- ACK 번호: "네가 보낸 데이터는 몇 번 직전까지 다 받았어"

A가 보내는 순서 번호와 B가 보내는 순서 번호는 서로 관계없는 별개의 번호이다.

### TCP 특징 한눈에 보기 (TCP Overview)

> 핵심
> 
> TCP는 일대일, 신뢰성 있고 순서가 보장되는 바이트 스트림, 전이중, 누적 ACK, 파이프라이닝, 연결 지향, 흐름 제어를 특징으로 한다.

- 일대일 <mark class="pink">(point-to-point)
  - 송신자 하나, 수신자 하나
- 신뢰성 있고 순서가 보장되는 바이트 스트림 <mark class="pink">( reliable, in-order byte stream)</mark>
  - "메시지 경계"가 없다.
- 전이중 데이터 <mark class="pink">(full duplex data)</mark>
  - 같은 연결 안에서 양방향으로 데이터가 흐른다.
  - MSS: 최대 세그먼트 크기 (maximum segment size)
- 누적 ACK <mark class="pink">(cumulative ACKs)</mark>
- 파이프라이닝 (pipelining)
  - TCP의 혼잡 제어와 흐름 제어가 윈도 크기를 정한다.
- 연결 지향<mark class="pink"> (connection-oriented)</mark>
  - 핸드셰이킹(제어 메시지 교환)으로 데이터를 주고받기 전에 송신자와 수신자의 상태를 초기화한다.
- 흐름 제어 <mark class="pink">(flow controlled)</mark>
  - 송신자는 수신자가 감당하지 못할 만큼 보내지 않는다.

관련 RFC

| RFC | 내용 |
|---|---|
| 793 | 최초의 TCP 표준 (1981) |
| 1122 | 인터넷 호스트 요구사항 |
| 2018 | 선택적 ACK (SACK) |
| 5681 | TCP 혼잡 제어 |
| 7323 | 고성능을 위한 TCP 확장 (윈도 스케일, 타임스탬프) |
| 9293 | 최신 TCP 표준 (2022년 8월) |

- 793: 원래 표준 (The original standard)
- 9293: 2022년 8월에 발표된 최신 TCP 표준
- 일부 RFC: 대부분의 TCP 구현에 포함되지만, 반드시 요구되지는 않음

파이프라이닝은 ACK를 기다리지 않고 여러 세그먼트를 연달아 보내는 것이다.
한 번에 얼마나 보낼지(윈도 크기)는 흐름 제어와 혼잡 제어가 정한다.

## 4. TCP 헤더와 캡슐화 (TCP Header and Encapsulation)

지금까지 본 TCP의 서비스와 특징은 결국 TCP 헤더의 필드들로 구현된다.
이번 파트에서는 TCP 세그먼트가 IP 데이터그램에 어떻게 담기는지 보고, 헤더의 각 필드가 어떤 역할을 하는지 하나씩 살펴본다.

### TCP 세그먼트의 캡슐화 (Encapsulation)

> 핵심
> 
> TCP 세그먼트는 IP 데이터그램 안에 담기며, TCP 헤더는 옵션이 없으면 20바이트, 옵션이 있으면 최대 60바이트이다.

- TCP 세그먼트는 IP 데이터그램 안에 캡슐화된다.
  - TCP 헤더는 옵션이 없을 때 보통 20바이트이다.
  - 옵션이 있으면 TCP 헤더는 최대 60바이트까지 커질 수 있다.
    - 자주 쓰이는 옵션: 최대 세그먼트 크기(MSS), 타임스탬프(Timestamps), 윈도 스케일(Window Scaling), 선택적 ACK(SACK)


IP 데이터그램의 데이터 부분 전체가 TCP 세그먼트(TCP 헤더 + TCP 데이터)이다.

### TCP 헤더 구조 (TCP Segment Structure)

> 핵심
> 
> TCP는 연결 양 끝이 현재 상태를 계속 맞춰(동기화해) 두어야 하는 훨씬 복잡한 프로토콜이기 때문에, 헤더도 UDP보다 복잡하다.

- TCP는 연결의 각 끝이 현재 상태를 알고 있도록(동기화되도록) 유지해야 하는, 훨씬 복잡한 프로토콜이다. 그래서 헤더도 UDP보다 복잡하다.

TCP 세그먼트 구조 (가로 32비트)
![](/assets/img/20261013-capture-3.png)

| 필드 |
|---|
| 출발지 포트 번호 (16비트) / 목적지 포트 번호 (16비트) |
 | 순서 번호 (sequence number, 32비트) |
| 확인 응답 번호 (acknowledgement number, 32비트) |
| 헤더 길이 (len) / 사용 안 함 (not used) / 플래그 C E U A P R S F / 수신 윈도 (receive window) |
| 체크섬 (checksum) / 긴급 데이터 포인터 (Urg data pointer) |
| 옵션 (options, 가변 길이) |
| 응용 데이터 (application data, 가변 길이) |

- sequence number : 이 세그먼트에 담긴 첫 바이트의 바이트 스트림 내 위치(offset)
- ACK number : 다음에 받기를 기대하는 바이트 번호 (= 여기 직전까지 다 받았음)
- header length : TCP 헤더 길이(바이트) ÷ 4 (20바이트 → 5, 60바이트 → 15)
- receive window (flow control) : 수신자가 지금 더 받을 수 있는 바이트 수
- checksum : 헤더 + 데이터 + 의사 헤더로 계산한 오류 검출 값, 틀리면 ACK 없이 버림

### 포트 번호 필드 (Port Number Fields)

> 핵심
> 
> TCP 헤더의 출발지, 목적지 포트 번호는 IP 헤더의 출발지, 목적지 IP 주소와 함께 각 연결을 유일하게 구분한다. IP 주소와 포트 번호의 조합을 소켓(또는 끝점)이라고 한다.

- 포트 번호 필드
  - 모든 TCP 헤더에는 출발지 포트 번호와 목적지 포트 번호가 들어 있다.
  - 이 두 값은 IP 헤더의 출발지, 목적지 IP 주소와 함께 각 연결을 유일하게 구분한다.
    - 따라서 소켓(또는 끝점) 한 쌍이 각 TCP 연결을 유일하게 구분한다.
      - 이는 네트워크 트래픽 모니터링에서 중요하다.

### 순서 번호 필드 (Sequence Number Field)

> 핵심
> 
> 순서 번호는 세그먼트의 첫 데이터 바이트가 스트림에서 몇 번째 바이트인지를 나타내는 32비트 값이다. 연결을 맺을 때 각 방향의 첫 세그먼트(SYN)에 무작위로 정한 초기 순서 번호(ISN)를 적으며, SYN은 순서 번호 하나를 소비한다.

- 순서 번호(Sequence Number) 필드
  - 송신 TCP에서 수신 TCP로 가는 데이터 스트림에서, 
  이 세그먼트의 첫 데이터 바이트가 어느 바이트인지를 나타낸다.
  - TCP는 바이트 하나하나에 순서 번호를 매긴다.
  - 순서 번호는 32비트 부호 없는 수이며, 2³² − 1에 도달하면 다시 0으로 돌아간다<mark class="pink">(wrap around)</mark>.
  - 연결을 맺을 때, 각 방향의 첫 세그먼트에서 SYN 비트가 켜진다.
    (첫 번째를 SYN 세그먼트, 두 번째를 SYNACK 세그먼트라고 한다.)
    - 이때 순서 번호 필드에는 그 방향에서 사용할, 무작위로 생성된 초기 순서 번호(ISN, Initial Sequence Number)가 들어간다.
    - 두 세그먼트에는 데이터가 없지만 SYN 비트가 순서 번호 하나를 소비하므로,
      같은 방향에서 데이터를 담은 첫 세그먼트의 순서 번호는 ISN + 1이 된다.

| 항목 | 내용 |
|---|---|
| 크기 | 32비트 (0 ~ 2³² − 1, 약 43억) |
| 다 쓰면 | 다시 0부터 (wrap around) |
| 시작값 | 방향마다 무작위로 정한 ISN |
| 첫 데이터 바이트 번호 | ISN + 1 (SYN이 번호 하나를 사용하므로) |

예를 들어 A의 ISN이 10,000이라면

| A → B 세그먼트 | 순서 번호 | 데이터 |
|---|---|---|
| SYN | 10,000 | 없음 |
| 첫 데이터 세그먼트 | 10,001 | 1,000바이트 |
| 다음 데이터 세그먼트 | 11,001 | 1,000바이트 |

B → A 방향은 B가 따로 정한 ISN으로 시작한다.

ISN을 0이 아니라 무작위로 정하는 이유?.
- 헷갈림 방지: 같은 4-튜플로 연결을 끊었다가 다시 맺었는데,
 이전 연결의 늦게 도착한 세그먼트가 새 연결 데이터로 착각될 수 
있다. 시작 번호가 매번 다르면 이런 일이 거의 안 생김.
- 보안: 시작 번호를 쉽게 예측할 수 있으면, 
공격자가 순서 번호를 맞춘 가짜 세그먼트를 끼워 넣을 수 있다. 
무작위면 맞추기 어렵다.

SYN 세그먼트 하나 보낼때도 순서번호 1 소비한다.

### 확인 응답 번호 필드 (Acknowledgment Number Field)

> 핵심
> 
> 확인 응답 번호는 ACK를 보내는 쪽이 다음에 받기를 기대하는 순서 번호, 즉 순서대로 잘 받은 마지막 바이트의 번호 + 1이다. 이 값은 ACK 비트가 켜져 있을 때만 유효하다.

- 확인 응답 번호(Acknowledgment Number, ACK) 필드
  - ACK를 보내는 쪽이 다음에 받기를 기대하는 순서 번호가 들어간다.
    - 즉, 성공적으로 받은 마지막 데이터 바이트의 순서 번호 + 1이다.
  - 이 필드는 ACK 비트가 켜져 있을 때만 유효하다.
    - 보통 처음과 마지막 세그먼트를 제외한 모든 세그먼트에서 켜져 있다.
  - 원래 TCP는 "누적 긍정 확인 응답을 쓰는 슬라이딩 윈도 프로토콜(a sliding window protocol with cumulative positive acknowledgments)"로 설명되었다.
    - ACK 번호는 수신자가 순서대로 받은 가장 큰 바이트(+ 1)를 나타내도록 만들어져 있다.
  - 하지만 현대의 TCP에는 선택적 확인 응답(SACK) 옵션이 있어, 수신자가 순서가 어긋났지만 제대로 받은 데이터를 송신자에게 알릴 수 있다.
  - TCP는 중복 확인 응답(같은 ACK 필드 값을 가진 여러 세그먼트)을 혼잡 제어와 오류 제어에 활용한다.

| 개념 | ACK 번호로 표현하는 방법 |
|---|---|
| 누적 ACK | 순서대로 받은 마지막 바이트 + 1 |
| 긍정 확인 응답 | "받은 것"만 알린다. "못 받은 것"을 직접 알리지는 않는다 |
| SACK (옵션) | 중간이 빠졌을 때, 그 뒤에 따로 받은 범위를 옵션 칸에 적어 알린다 |
| 중복 ACK | 같은 ACK 번호가 반복되면 중간 세그먼트가 빠졌다는 신호로 쓴다 |

예: 101 ~ 200번 바이트 세그먼트가 사라지고, 201 ~ 400번 바이트가 도착한 경우

| 방식 | 수신자가 보내는 정보 |
|---|---|
| 누적 ACK만 | ACK 101 (반복 → 중복 ACK) |
| 누적 ACK + SACK | ACK 101, SACK: 201 ~ 400번 받음 |

### 헤더 길이 필드와 플래그 (Header Length and Flags)

> 핵심
> 
> 헤더 길이 필드는 TCP 헤더 길이를 32비트(4바이트) 단위로 나타내며, 4비트이므로 헤더는 최대 60바이트이다. 플래그 필드는 8개의 비트로 세그먼트의 성격을 표시한다.

- 헤더 길이(Header Length) 필드
  - 헤더의 길이를 32비트 워드(word) 단위로 나타낸다.
  - 옵션 필드의 크기가 가변적이기 때문에 필요하다.
  - 4비트 필드이므로, TCP 헤더는 최대 60바이트로 제한된다.
- 8비트 플래그(Flag) 필드


| 플래그                           | 분류 | 의미                               |
|-------------------------------|---|----------------------------------|
| CWR                           | 혼잡 알림 | 혼잡 알림을 받고 전송 속도를 줄였다             |
| ECE                           | 혼잡 알림 | 네트워크에서 혼잡 알림을 받았다고 상대에게 전한다      |
| <mark class="pink">URG</mark> | 데이터 처리 | 긴급 데이터가 있다 (급한건 다르게 처리해라)        |
| <mark class="pink">ACK     </mark>   | 확인 응답 | ACK 번호가 유효하다                     |
| <mark class="pink">PSH </mark>       | 데이터 처리 | 버퍼에 모으지 말고 바로 응용 프로그램에 넘겨라 (급해!) |
| <mark class="pink">RST </mark>       | 연결 관리 | 연결을 강제로 끊는다 (연결 초기화 하자)          |
| <mark class="pink">SYN</mark>       | 연결 관리 | 연결을 시작한다 (ISN 전달)                |
| <mark class="pink">FIN  </mark>      | 연결 관리 | 보낼 데이터가 끝났다 (연결 종료 시작)           |

색칠한건 예전 제어 플래그 필드이다.
앞의 CWR, ECE 두 개는 나중에 추가된 혼잡 알림(ECN)용 플래그이다.

### [참고] 예전의 제어 플래그 필드 (Older Control Flag Fields)

헤더의 네 번째 행(32비트)이 시대에 따라 어떻게 나뉘었는지 비교하면 다음과 같다.

| 구분 | 헤더 길이 | 예약 | 플래그 | 윈도 크기 |
|---|---|---|---|---|
| RFC 793 (1981) | 4비트 (Data Offset) | 6비트 | 6비트: URG, ACK, PSH, RST, SYN, FIN | 16비트 |
| 현재 | 4비트 | 4비트 | 8비트: CWR, ECE, URG, ACK, PSH, RST, SYN, FIN | 16비트 |

원래 비워 두었던 예약 영역의 일부를 나중에 혼잡 알림(ECN)용 플래그인 CWR, ECE로 사용하게 되었다.
그래서 오래된 구현은 뒤의 6개 플래그만 이해한다.

### 윈도 크기 필드 (Window Size Field)

> 핵심
> 
> 윈도 크기는 ACK 번호가 가리키는 바이트부터 수신자가 받을 수 있는 바이트 수이며, 각 끝점은 이 값을 알려 흐름 제어를 한다. 16비트라 최대 65,535바이트로 제한되지만, 윈도 스케일 옵션으로 더 크게 늘릴 수 있다.

- 윈도 크기(Window Size) 필드
  - ACK 번호로 지정된 바이트부터 시작해, 수신자가 받을 의향이 있는 바이트 수이다.
    - 각 끝점이 이 필드로 윈도 크기를 알림(advertise)으로써 흐름 제어가 이루어진다.
  - 16비트 필드이므로 윈도는 65,535바이트로 제한되며, 이 때문에 TCP의 처리량 성능도 제한된다.
    - 하지만 윈도 스케일(Window Scale) 옵션을 쓰면 이 값을 배율로 키울 수 있어,
      고속, 장거리(긴 지연) 네트워크에서 훨씬 큰 윈도와 더 나은 성능을 얻을 수 있다.

| 항목 | 내용                                         |
|---|--------------------------------------------|
| 의미 | ACK 번호부터 수신자가 더 받을 수 있는 바이트 수              |
| 역할 | 흐름 제어 (송신자가 수신자를 넘치게 하지 않음)                |
| 크기 | 16비트, 최대 65,535바이트 = 64KB                  |
| 확장 | 윈도 스케일 옵션: 윈도 값에 2의 거듭제곱 배율을 곱함 (최대 약 1GB) |

예: ACK 번호가 5,001이고 윈도 크기가 3,000이면,
송신자는 5,001 ~ 8,000번 바이트까지 ACK를 기다리지 않고 보낼 수 있다.

윈도 크기가 처리량을 제한하는 이유

- TCP는 한 RTT 동안 최대 윈도 크기만큼만 보낼 수 있다.
- 최대 처리량 ≈ 윈도 크기 ÷ RTT
- 예: 윈도 65,535바이트, RTT 100ms → 약 655KB/s ≈ 5.2Mbps

링크가 아무리 빨라도 윈도가 작으면 이 이상 보낼 수 없으므로, 윈도 스케일 옵션이 필요하다.
- window scale option : 윈도 크기칸이 16비트라 최대 약 64KB밖에 못적는 문제를 해결한다.
- 예를 들어 1Gbps 회선에 RTT가 100ms라면 BDP(대역폭 × 지연)는 약 12.5MB이다.
회선을 꽉 채우려면 이만큼의 데이터를 ACK 없이 연달아 보낼 수 있어야 하는데,
윈도가 64KB라면 조금 보내고 ACK를 기다리는 일을 반복하느라 회선의 극히 일부만 쓰게 된다.

이 문제를 해결하는 것이 윈도 스케일 옵션이다.
헤더의 윈도 크기 칸은 그대로 16비트로 두고, 연결을 맺을 때 "앞으로 적는 윈도 값에 배율을 곱해서 읽자"고 미리 약속한다.

실제 윈도 크기 = 헤더에 적힌 윈도 값 × 2^(시프트 값)

| 시프트 값 | 배율 | 헤더에 1,000이라고 적었을 때 |
|---|---|---|
| 0 | 1배 | 1,000바이트 |
| 7 | 128배 | 128,000바이트 |
| 14 (최대) | 16,384배 | 16,384,000바이트 |

동작 방식은 다음과 같다.

- 연결을 맺을 때 SYN 세그먼트의 옵션 칸에 시프트 값을 적어 보낸다.
- 양쪽이 모두 이 옵션을 보내야 사용된다. 한쪽이라도 보내지 않으면 둘 다 사용하지 않는다.
- 시프트 값은 방향마다 따로 정할 수 있다.
- 한 번 정하면 연결이 끝날 때까지 바꿀 수 없다.

배율이 커질수록 윈도를 세밀하게 표현하는 정밀도는 떨어지지만(배율 128이면 128바이트 단위),
고속 네트워크에서는 문제가 되지 않아 대부분의 운영체제가 기본으로 사용한다.
이 옵션은 RFC 7323(고성능을 위한 TCP 확장)에 정의되어 있다.

#### 최대 시프트 값이 14인 이유

시프트 값의 최댓값 14는 순서 번호가 32비트라는 데서 나온다.

순서 번호는 2³² − 1 다음에 다시 0으로 돌아가므로, 일직선이 아니라 둘레가 2³²인 원 위의 숫자처럼 동작한다.
이 원 위에서 두 번호의 앞뒤를 판단하려면, 두 번호 사이의 거리가 원의 절반(2³¹)보다 작아야 한다.
시계로 비유하면, 지금이 3시일 때 9시는 6시간 뒤인지 6시간 전인지 알 수 없는 것과 같다.

TCP에서는 송신 쪽과 수신 쪽 윈도를 합친 범위가 2³¹을 넘지 않아야 하므로, 한쪽 윈도는 2³⁰(약 1GB)보다 작아야 한다.

| 시프트 값 | 최대 윈도 | 2³⁰과 비교 |
|---|---|---|
| 14 | 65,535 × 2¹⁴ = 2³⁰ − 2¹⁴ (약 1GB) | 2³⁰보다 작음 → 가능 |
| 15 | 65,535 × 2¹⁵ ≈ 2³¹ (약 2GB) | 2³⁰을 넘음 → 불가능 |

즉, 윈도 16비트와 시프트 14를 합친 30비트가 순서 번호 공간 안에서 안전하게 쓸 수 있는 최대 크기이다.
덕분에 윈도를 크게 키워도 새 세그먼트와 한 바퀴 전의 옛날 세그먼트를 헷갈리지 않는다.


### 체크섬 필드 (TCP Checksum Field)

> 핵심
> 
> TCP 체크섬은 TCP 헤더와 데이터, 그리고 IP 헤더의 일부 필드까지 포함해 계산하며, 송신자는 반드시 계산해 넣고 수신자는 반드시 확인해야 한다.

- TCP 체크섬(Checksum) 필드
  - UDP와 비슷한 의사 헤더(pseudo-header) 계산 방식을 써서, TCP 헤더와 데이터, 그리고 IP 헤더의 일부 필드를 포함한다.
  - 송신자는 이 필드를 반드시 계산해 저장해야 하고, 수신자는 반드시 검증해야 한다.

| 항목 | 내용 |
|---|---|
| 크기 | 16비트 |
| 계산 범위 | 의사 헤더 + TCP 헤더 + TCP 데이터 |
| 송신자 | 반드시 계산해서 넣음 |
| 수신자 | 반드시 다시 계산해서 비교 |
| 틀리면 | 세그먼트를 버리고 ACK를 보내지 않음 |

UDP에서는 체크섬이 선택 사항(IPv4에서 0이면 계산 안 함)이지만, TCP에서는 필수(mandatory)이다.

### TCP 의사 헤더 (Pseudoheader)

> 핵심
> 
> TCP 체크섬을 계산할 때는 세그먼트 앞에 IP 헤더의 일부로 만든 의사 헤더를 잠시 붙여 함께 계산한다. 의사 헤더는 실제로 전송되지 않는다.

- TCP 세그먼트에 덧붙이는 의사 헤더

### 송신 측 체크섬 계산 예제 (Example of Checksum Calculation at the Sender)

> 핵심
> 
> 인터넷 체크섬은 체크섬 칸을 0으로 둔 채 데이터를 16비트 단위로 나눠 1의 보수 덧셈으로 모두 더하고, 그 결과를 뒤집어(1의 보수) 체크섬 칸에 넣는다.

문제

- 아래 헤더의 체크섬을 송신 측에서 계산하라.


| 필드 | 값 |
|---|---|
| 버전, 헤더 길이, 서비스 유형 | 4, 5, 0 |
| 전체 길이 | 28 |
| 식별자, 플래그, 단편 오프셋 | 1, 0, 0 |
| TTL, 프로토콜 | 4, 17 |
| 체크섬 | 0 (계산 전) |
| 출발지 IP 주소 | 10.12.14.5 |
| 목적지 IP 주소 | 12.6.7.9 |

계산 과정

| 16비트 단위 | 값 (16진수) |
|---|---|
| 4, 5, 0 | 4500 |
| 28 | 001C |
| 1 | 0001 |
| 0, 0 | 0000 |
| 4, 17 | 0411 |
| 체크섬 (0) | 0000 |
| 10.12 | 0A0C |
| 14.5 | 0E05 |
| 12.6 | 0C06 |
| 7.9 | 0709 |
| 합계 | 744E |
| 1의 보수 (체크섬) | 8BB1 |

정답

- 체크섬 = 8BB1 (16진수)

설명

인터넷 체크섬 계산 순서는 다음과 같다.

1. 체크섬 칸을 0으로 채운다.
2. 전체를 16비트(2바이트) 단위로 나눈다.
3. 모두 더한다. 16비트를 넘는 자리올림이 생기면 맨 아래 비트에 다시 더한다. (1의 보수 덧셈)
4. 결과의 모든 비트를 뒤집는다. (1의 보수) 이것이 체크섬이다.

이 예제에서는 합계가 744E이고, FFFF − 744E = 8BB1이 체크섬이 된다.

수신 측은 체크섬까지 포함해 다시 모두 더한다.
744E + 8BB1 = FFFF이고, 이를 뒤집으면 0이 되므로 오류가 없다고 판단한다.
결과가 0이 아니면 어딘가 비트가 바뀐 것이므로 버린다.

TCP 체크섬도 같은 방법으로 계산하며, 계산 범위만 의사 헤더 + TCP 헤더 + 데이터로 다르다.
